# web: the browser checker

> **Human review: none.** Generated by AI (Claude Code, Claude Opus 5.5) under the
> direction of Nicolas Jonason, 2026-11-06.

A static page that runs the rule engine in the browser: paste Swedish text, get
a verdict (translated from English / original Swedish / unclear), P(translated),
the clues highlighted in the text, and the evidence for each side. No server,
no network requests after the page has loaded. Live at
<https://erl-j.github.io/translationese-detector/>.

| path | what |
|---|---|
| `site/` | the deployable site, served as is (no build step at serve time) |
| `site/tsw.js` | hand-written JavaScript port of `tsw/`: normaliser with offset map, sentence splitter, tokenizer, Doc views, rule types, the PredicateRules, engine |
| `site/ruleset.json` | **generated** by `build_ruleset.py`; do not edit |
| `site/index.html`, `app.js`, `style.css`, `favicon.svg` | the page |
| `build_ruleset.py` | exports rules, parameters, derived constants, labels, word lists and regexes from the live Python objects |
| `pyre2js.py` | Python `re` → JavaScript `RegExp` (v flag) translator, via `sre_parse` |
| `export_parity.py` | Python reference results for the parity test (writes `parity/`, gitignored: it contains Europarl text) |
| `parity_test.ts` | Deno test: JS port vs Python |

## Rebuild after changing the rules

From the repository root:

```bash
# 1. regenerate the ruleset (a few seconds)
python3 -I web/build_ruleset.py

# 2. Python reference results: 2000 trn texts (sentences + 100-token chunks, fixed seed),
#    one long text, all unit-test strings, edge cases. trn only, never val or test. ~20 s.
python3 -I web/export_parity.py

# 3. parity test against the exact files in web/site/ (~5 s)
deno test --allow-read web/parity_test.ts

# 4. commit web/site/ on main and push: .github/workflows/pages.yml deploys it
```

Deno ships with Quarto (`<quarto>/bin/tools/<arch>/deno`) if it is not installed.
If the builder stops with "unknown StatRule unit function" or "PredicateRule
without a JS port", a rule needs code that has to be ported to `tsw.js` by hand
first. A new regex construct that has no faithful JavaScript equivalent stops
`pyre2js.py` the same way.

To try the site locally: `python3 -m http.server -d web/site 8000` and open
<http://localhost:8000/> (opening `index.html` as a file does not work: the page
fetches `ruleset.json`).

## Deployment (GitHub Pages)

`.github/workflows/pages.yml` uploads `web/site/` and deploys it on every push
to `main` that touches `web/site/**` (or by hand: Actions → pages → Run
workflow). **One-time setup by the repository owner:** Settings → Pages →
Build and deployment → Source = **GitHub Actions**. All URLs in the site are
relative, so it works under the project subpath `/translationese-detector/`.

## Parity with Python

What `parity_test.ts` checks, per text: score and P(translated) (relative
tolerance 1e-6), per-rule contributions, per-family sums, every highlighted
span (offsets, rule, direction, label, share), document-level evidence and its
wording, the evidence sentences, word and sentence counts, the normalised text
and sentence spans, and the matches of each of the 56 regexes (rule patterns, tokenizer, splitter) on its own.
A second test sweeps all code points through the character predicates the port
uses (`isalnum`, `isalpha`, `isupper`, `isdigit`, `\w`, `\s`, `lower()`).

Result at commit time: **2782/2782 texts match; all scores are bit-identical**
(2000 trn texts, 1 long text, 755 unit-test strings, 26 edge cases; 17,832 spans
and 173,885 regex matches compared). The code-point sweep differs from Python
3.9 only on code points that are unassigned in Python's Unicode 13 database
(letters and digits added in later Unicode versions, which the browser knows).

Where the port differs from Python by design:

- **Offsets are UTF-16 code units** (what the browser needs), Python's are code
  points; they differ only after characters outside the Basic Multilingual Plane
  (emoji). The test converts before comparing.
- **Unicode version**: the browser's Unicode tables are newer than Python 3.9's
  (Unicode 13). Characters added since then count as letters/digits in the page
  but not in Python.
- **Regex alternation order**: `words_rx()` and `TOKEN_RX` order equal-length
  alternatives by Python set iteration, which depends on the per-process hash
  seed, so `ruleset.json` can differ textually between builds. The matches are
  the same (equal-length whole-word alternatives cannot both match at one
  position).
- **Floating point**: the port repeats Python's operations in the same order and
  takes all logarithms of parameters from Python (in the ruleset), so results
  are bit-identical in practice; `Math.log`/`Math.exp` on per-text values may in
  principle differ from C's in the last bit, hence the tolerance.
- The page asks for all evidence (`annotate(text, Infinity)`), not Python's top 5.

The page needs RegExp `v`-flag support (Chrome/Edge 112+, Firefox 116+,
Safari 17+); older browsers get a message instead of a verdict.
